# Codebase Reference

A map of the template: where things live, how the pieces fit together, and
the conventions that aren't obvious from reading a single file. See
[../AGENTS.md](../AGENTS.md) for commands and the short list of conventions,
and [PROJECT.md](PROJECT.md) for product context.

This file is deliberately a map, not a spec — it points at the module that
owns each behavior instead of restating its implementation. Prefer that
module's `@moduledoc`/`@doc` over this file when the two disagree; code and
docstrings change together, this file might not.

---

## Layout

```
lib/my_app/               # Domain layer (Ash resources & domains)
  accounts.ex             # Ash Domain — User, Token, UserIdentity
  accounts/               # Resources, senders (magic link email)
  secrets.ex              # AshAuthentication.Secret — maps auth secrets to app config
  shared/enum_data.ex     # EnumData — Ash.Type.Enum with per-value data
  oban_reporter.ex        # Oban telemetry → Sentry
lib/my_app_web/
  router.ex               # Pipelines, auth routes, admin routes (/oban, /dev)
  components/core/        # UI component system (see below)
  components/cinder/      # Cinder table theme, controls, filter overrides
  live/index.ex           # MyAppWeb.Start.Index — the "/" LiveView
  hooks/                  # on_mount: LiveUserAuth, LiveLocale
  plugs/                  # CSP (nonce), EnsureAdmin, Health
  auth_overrides.ex       # AshAuthentication UI overrides
lib/mix/tasks/template.setup.ex   # `mix template.setup <Name>` — rename the template
```

## Domain layer

### Accounts

`MyApp.Accounts` is the only Ash domain (`config :my_app, ash_domains: [...]`), holding `User`, `Token`, and `UserIdentity` (tables `users`, `tokens`, `user_identities`). An ER diagram is checked in at `lib/my_app/accounts-mermaid-er-diagram.md` (regenerated by `mix docs`).

`MyApp.Accounts.User` (`lib/my_app/accounts/user.ex`) is the one resource worth reading before touching auth — its DSL blocks and inline comments are the source of truth for strategies, tokens, and policies. A few things that aren't visible from a quick skim:

- **OIDC is IdP-agnostic and gated at compile time.** The `oidc :sso` strategy is wrapped in `if Application.compile_env(:my_app, :oidc_enabled)` — the flag comes from `OIDC_ENABLED`, read in `config.exs`, so toggling it needs a recompile. Secrets resolve at runtime via `MyApp.Secrets` from `OIDC_*` env vars; `runtime.exs` raises at boot if the compiled flag and the runtime vars disagree. Works with Zitadel, Entra ID, or any OIDC IdP.
- **Roles, not an admin boolean.** `roles` is a plain `{:array, :string}` attribute filled by `register_with_sso` from IdP claims (Zitadel's role-map claim or a plain `roles` list, e.g. Entra ID). "Admin" means `"admin" in user.roles` — see `MyAppWeb.Plugs.EnsureAdmin`.
- **No user-facing policies yet.** The only policy is the `AshAuthenticationInteraction` bypass, so reads outside authentication flows need `authorize?: false` (or new policies as the app grows).

`MyApp.Secrets` (`use AshAuthentication.Secret`) maps `:token_signing_secret` and the `oidc_*` config keys to the auth DSL's secret slots.

### EnumData

`MyApp.Shared.EnumData` (`lib/my_app/shared/enum_data.ex`) is the way to define domain constants: an `Ash.Type.Enum` enriched with per-value metadata (icons, badge classes, arbitrary flags) and gettext-translated labels, so a value's presentation lives next to its definition instead of scattering `case` statements across templates.

```elixir
defmodule MyApp.Posts.Types.Status do
  use MyApp.Shared.EnumData,
    values: [
      draft:     [label: gettext("Draft"),     meta: [icon: "tabler-eye-closed", badge_class: "badge-ghost"]],
      published: [label: gettext("Published"), meta: [icon: "tabler-eye",        badge_class: "badge-success"]]
    ]
end
```

Full usage — defining values, `meta/1,2`, `options/0` for selects, displaying a value in a template — is documented in the module's `@moduledoc`; read that before adding a new enum. `test/my_app/shared/enum_data_test.exs` is the reference for the full behavior (the template ships no consumer yet).

### Jobs & state machines

Oban runs its Cron/Lifeline/Pruner services; the supervisor starts it through `AshOban.config/2`, so `oban do ... end` trigger blocks on resources are picked up automatically — none are defined yet. Likewise `ash_state_machine` is wired (dep, formatter import, `mix docs` flow charts) but no resource uses it yet. `MyApp.ObanReporter` forwards `[:oban, :job, :exception]` telemetry to Sentry.

## Web layer

### Router (`lib/my_app_web/router.ex`)

- **Pipelines**: `:locale` (session, `Cldr.Plug.PutLocale` from query/path/route/session/accept-language, CSRF, `assign_current_locale`, `Cldr.Plug.PutSession`) and `:browser` (root layout, static CSP fallback via `put_secure_browser_headers`, then `MyAppWeb.Plugs.CSP` for the per-request nonce, `load_from_session`).
- **App routes**: `ash_authentication_live_session :authenticated_routes` (with `LiveLocale` on_mount) holds `live "/", Start`. Auth hooks for new live_sessions come from `MyAppWeb.Hooks.LiveUserAuth`: `:live_user_required` (redirects to `/sign-in`), `:live_user_optional`, `:live_no_user`.
- **Auth routes**: `auth_routes`/`sign_out_route` for `AuthController`, `sign_in_route` (with `MyAppWeb.AuthOverrides` + the DaisyUI/Default override stack), `magic_sign_in_route`.
- **Admin routes** — behind `MyAppWeb.Plugs.EnsureAdmin`: `/dev/dashboard` (LiveDashboard), `/dev/mailbox` (Swoosh preview), `/oban` (Oban Web).

### Plugs & hooks

- `MyAppWeb.Plugs.CSP` — generates a nonce per request, assigns `:csp_nonce_value` (consumed by the inline theme script in `root.html.heex`).
- `MyAppWeb.Plugs.EnsureAdmin` — halts with **404** (not 403) unless `"admin" in user.roles`.
- `MyAppWeb.Plug.Health` — mounted before everything, answers `200 "OK"` on `/health`.
- `MyAppWeb.Hooks.LiveLocale` — restores the CLDR/gettext locale from the session on every LiveView mount.

### Helpers & errors

`MyAppWeb.Helpers` (auto-imported) provides `ok/1`, `noreply/1`, `assign_noreply/2`, `patch_params/2,3`, `params_has_key?/2`, `calc/2` — see the module's docs for each. `MyAppWeb.Error.handle_error/2` (auto-imported) turns `Ash.Error.Invalid` into batched error toasts and logs everything else.

## The core component system

Prefer the core component system (`lib/my_app_web/components/core/`) over hand-rolled primitives (raw `<button>`, `<input>`, ad-hoc styled boxes) — most needs already have a component, and a missing one should follow the pattern below rather than being inlined. Components are thin wrappers around daisyUI classes; extend with daisyUI modifiers, not custom CSS.

### Auto-imported vs facade access

`html_helpers/0` in `lib/my_app_web.ex` auto-imports only `Icon`, `Button`, `Badge`, and `Utils` (`show/hide` JS transitions, `translate_error(s)`) — so `<.icon>`, `<.button>`, `<.badge>` work everywhere. Everything else goes through a **facade module per group**, aliased at the call site:

```elixir
alias MyAppWeb.Components.Core

~H"""
<Core.Inputs.text field={@form[:email]} label={gettext("Email")} />
<Core.Containers.modal id="confirm">...</Core.Containers.modal>
"""
```

Each group has a facade file that `defdelegate`s (with `@spec`) to one-file-per-component submodules — its `@moduledoc` lists what it holds:

```elixir
defmodule MyAppWeb.Components.Core.Containers do
  use MyAppWeb, :html
  alias MyAppWeb.Components.Core.Containers

  @spec modal(map()) :: Rendered.t()
  defdelegate modal(assigns), to: Containers.Modal
end
```

### Inventory

| Facade            | Components                                                                                                                                                                                                |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| _(auto-imported)_ | `icon`, `button`, `badge`, `Utils`; `Core.Toast` (module, not a component)                                                                                                                                |
| `Core.Inputs`     | `hidden`, `text`, `textarea`, `number`, `select`, `combobox`, `multi_select`, `checkbox`, `switch`, `radio`, `file`, `range`, `date` — plus support modules `Inputs.Listbox` and `Inputs.Listbox.Options` |
| `Core.Containers` | `drawer`, `empty_state`, `modal`                                                                                                                                                                          |
| `Core.Navigation` | `simple_link`, `dropdown`                                                                                                                                                                                 |
| `Core.Layouts`    | `app`, `flash_group`, `locale_switcher`, `theme_toggle`, `root.html.heex` (embedded template)                                                                                                             |

Each facade's `@moduledoc` is the fastest way to see what a group offers and how it composes — check it before this table if they disagree.

### Attr conventions

- Variants are atoms mapped to daisyUI classes with **one function clause per value** (`defp color_class(:primary), do: "btn-primary"`) — Tailwind's scanner cannot see interpolated class names.
- `<.button>`: `color` (`:neutral :primary :secondary :accent :info :success :warning :error`), `style` (`:solid :outline :soft :ghost :link`), `size` (`:xs..:xl`), `shape` (`:wide :block :square :circle`); renders a `<.link>` when `href`/`navigate`/`patch` is present. `<.badge>` mirrors colors/sizes.
- `<.icon name="tabler-x" class="size-4" />` — Tabler outline set (`-filled` suffix for filled), rendered as a span with the icon class (plugin `assets/vendor/tabler.js`).

### Form inputs

Every input follows the same skeleton (see `core/inputs/text.ex` as the canonical example): a two-clause entrypoint where the `%{field: %FormField{}}` clause pipes through `Inputs.prepare/1` and re-calls itself, then wraps its markup in `Inputs.field/1`. `Inputs.common_attributes()` supplies the shared attrs (`field`, `id`, `name`, `label`, `value`, `errors`, `validation_delayed?`, `class`, `error_class`, a `:description` slot).

The `MyAppWeb.Components.Core.Inputs` `@moduledoc`, and the docs on `prepare/1` and `field/1`, are the source of truth for the field/error/description contract (label placement, error translation, debounce behavior) — read those rather than assuming from one input's markup. When you need a new input, copy the `text.ex` skeleton; don't inline a raw `<input>`.

### Listbox inputs (select / combobox / multi_select)

The three dropdown inputs share `Inputs.Listbox` (the popover) and `Inputs.Listbox.Options` (pure option-pipeline helpers) — this part is genuinely non-obvious, so it's worth a few lines here:

- The popover uses the native `popover` attribute + **CSS anchor positioning** (`assets/css/components/combobox.css`), so it escapes `<dialog>`/overflow clipping. Each input owns its trigger and colocated JS hook (`.Select`, `.Combobox`, `.MultiSelect`); shared keyboard/ARIA logic lives in `assets/js/listbox.ts`.
- Options are `{label, value}` tuples or maps (`:label`, `:value`, plus optional `:search`, `:display`, `:badge`, arbitrary keys), optionally grouped.
- `select` — styled `<select>` replacement (no text search); `combobox` — searchable single-select; `multi_select` — searchable checkbox multi-select (values submit as `name[]` plus an always-present hidden `""` that consumers must reject).
- **Search wiring**: the parent LiveView owns the search term and filters the options — `search_name` (outside the form namespace), `search_term`, and an optional `search_event` (otherwise the form's `phx-change` fires). See `Inputs.Listbox.Options` for the exact option-pipeline API (`dropdown_groups/4`, `max_results` semantics).

### Containers & navigation

- `Core.Containers.modal` — native `<dialog>`; client API `Modal.show/1`/`Modal.hide/1`, server API `Modal.open/2`/`Modal.close/2`.
- `Core.Containers.drawer` — a modal in a full-height panel pinned to one screen edge (daisyUI `modal-start`/`modal-end`); same API as `modal`. `modal={false}` opens it with `show()` instead, leaving the page behind it live — no backdrop, no focus trap. For a URL-driven drawer, render it conditionally with `open_on_mount` and patch the query param away in `on_cancel`.
- `Core.Navigation.dropdown` — CSS-only `<details>`/`<summary>` daisyUI dropdown with a `:button` trigger slot.

### Layouts, toasts, theme, locale

- Begin every LiveView template with `<Layouts.app flash={@flash} current_user={@current_user} socket={@socket}>` — renders the navbar (locale switcher, theme toggle, sign-in/out), `<main>`, and the flash/toast group. Passing `socket={@socket}` makes toasts render live.
- Toasts: `Core.Toast.send_icon(:success, msg)` (or `send/2,3`) from any LiveView — a LiveToast wrapper with per-kind tabler icons; `put_flash` renders through the same group.
- Theme: `theme_toggle` dispatches `phx:set-theme`; persistence is the CSP-nonce'd inline script in `root.html.heex`.
- Locale: `locale_switcher` renders `?locale=xx` links (full page reload) for `Gettext.known_locales/1`.

### Adding a new core component

1. One file per component under the right group directory (`core/inputs/foo.ex` → `MyAppWeb.Components.Core.Inputs.Foo`), `@moduledoc false`, docs on the function, `attr`/`slot` declarations, `@spec foo(map()) :: Rendered.t()`.
2. Add a `defdelegate foo(assigns), to: Inputs.Foo` (with `@spec`) in the group facade, and update its `@moduledoc` list.
3. Reuse the existing color/size atom vocabularies and daisyUI classes — complete literal class names only.
4. Add a component test under `test/my_app_web/components/core/` (`render_component/2` + HTML assertions, as the existing input tests do).

### Hooks

A hook lives in one of two places, and which one is not a matter of taste:

- **`assets/js/hooks/*.ts`**, registered by name in the `hooks` map in `app.ts` — for a hook that more than one component mounts (`Dialog`, behind both `modal/1` and `drawer/1`). The component references it by bare name: `phx-hook="Dialog"`.
- **A colocated `<script>` in the component**, referenced as `phx-hook=".Foo"` — for behaviour that belongs to that one component's markup and nothing else. This is the common case.

Never write a colocated hook whose body only re-exports a class from `assets/js/`: that is a hook in the wrong place, not a composition point. Shared _helpers_ are different — `assets/js/listbox.ts` is a module of functions, not a `ViewHook`, and colocated hooks import it freely.

Colocated hooks are **written in TypeScript**:

```heex
<script :type={ColocatedHook} name=".Foo" extension="ts">
  import { ViewHook } from "phoenix_live_view";

  class Foo extends ViewHook {
    declare toggle: HTMLElement;

    mounted() {
      this.toggle = this.el.querySelector<HTMLElement>(".foo-toggle")!;
      this.el.addEventListener("keydown", (e) => this.onKeydown(e));
    }

    onKeydown(e: KeyboardEvent) { ... }
  }

  export default Foo;
</script>
```

- `extension="ts"` makes LiveView write the extracted file as `.ts` — without it bun and the formatter both treat the body as plain JS.
- The default export subclasses `ViewHook` (from `phoenix_live_view`), which gives `this.el`, `this.pushEvent`, etc. for free. State that a lifecycle method assigns rather than initializes inline — like `toggle` above — is declared with `declare` (type-only, no runtime field init that could stomp what `mounted()` sets); everything else (helper methods) is just a normal class method, typed directly on its own signature.
- The `phoenix_live_view` import resolves to the hex dependency's own bundled types through the `workspaces: ["../deps/*"]` entry in `assets/package.json`, which symlinks `deps/*` into `assets/node_modules`. That beats the community `@types/phoenix_live_view` package, which is stuck at 1.0.0 and doesn't model the subclassable `ViewHook` class. Don't add a `paths` mapping for it — bun reads `paths` when bundling too and would try to bundle the `.d.ts` file.
- Shared client code goes in `assets/js/` and is imported with the `@` alias (`import * as Listbox from "@/js/listbox"`), mapped to `assets/` by the `paths` entry in `tsconfig.json` — bun reads it when bundling, so no separate bundler alias is needed. The alias exists because a colocated hook is extracted to `_build`, outside `assets/`; files under `assets/js/` reach each other with plain relative imports.
- Linting and formatting use `prettier`, `eslint` and `tsc` and run through bun as `mix assets.lint` and `mix assets.format`. Each alias chains one `mix bun assets run <script>` call per tool

## Cinder tables

Use `Cinder.collection` for Ash-backed tables. The integration lives in `lib/my_app_web/components/cinder/` and is wired in `config.exs` (theme + custom filter types) — check there for the exact config keys.

- **Theme** — `MyAppWeb.Components.Cinder.Theme` (`extends(:daisy_ui)`): zebra table, daisyUI loading spinner, tabler sort icons, and hidden per-filter chrome because the custom controls render their own.
- **Controls** — pass `MyAppWeb.Components.Cinder.Controls.filter_controls/1` as the `:controls` slot for responsive filters (inline on desktop, a client-only drawer on mobile, plus a reset button):

```heex
<Cinder.collection resource={MyApp.Accounts.User} ...>
  <:controls :let={controls}>
    <MyAppWeb.Components.Cinder.Controls.filter_controls controls={controls} />
  </:controls>
</Cinder.collection>
```

- **Filters** — the `select`, `autocomplete`, and `multi_select` filter types implement `Cinder.Filter` and render the core listbox inputs. Autocomplete keeps its search term under `filters[<field>_autocomplete_search]` so Cinder's clear wipes it; multi_select adds a "Match all" mode via a `~mode:all` sentinel value. Shared plumbing sits in `filters/shared.ex`.
- `assets/css/app.css` has `@source "../../deps/cinder";` so Cinder's own classes are compiled.

## i18n

- **Backend**: `MyAppWeb.Gettext` holds the catalogues; nothing calls it directly. Translation goes through the `~t` sigil from [gettext_sigils](https://hexdocs.pm/gettext_sigils) — `~t"..."` = `gettext/1`, `~t"..."m` = `pgettext` with the **calling module** as msgctxt, `~t"..."e` = the `errors` domain, and `~t"..."N` pluralizes on a `count` binding. Controllers, LiveViews and components inherit it from `MyAppWeb`; a plain module writes `use MyAppWeb, :translations`. The modifiers are configured in `MyAppWeb.translations/0`. Because the msgctxt is the module name, moving a component that uses `~t"..."m` to another module changes its context → run `mix gettext.extract --merge` and re-confirm the fuzzy entries.
- **Domains**: `default`, `errors` (used by `translate_error/1`), and `auth` — the auth `.po` files are **hand-maintained** (ash_authentication_phoenix builds strings at runtime; they cannot be extracted).
- **Locales**: en, de, fr — both for gettext (`priv/gettext/`) and CLDR (`MyAppWeb.Cldr`, data in `priv/cldr/`).
- **Flow**: `?locale=xx` → `Cldr.Plug.PutLocale` → session → `LiveLocale` on_mount for LiveViews.
- `mix precommit` extracts/merges (`--no-fuzzy`); `mix lint` checks `gettext.extract --check-up-to-date`.

## Config & environment

Ash, Oban, Cinder, and the rest are configured in `config.exs`/`runtime.exs` — read those directly for current values rather than trusting a summary here. A few things worth knowing that aren't just config values:

- **The OIDC compile/runtime split** (see [Accounts](#accounts) above) is the one config-related gotcha likely to bite: the flag is compile-time, the secrets are runtime, and `runtime.exs` raises at boot if they disagree.
- **Don't reorder Ash DSL sections by hand** — `config.exs` pins a `section_order` for the Spark formatter; let `mix format` apply it.
- `.env.example` documents the dev-time env vars; prod adds `DATABASE_URL`, `SECRET_KEY_BASE`, `TOKEN_SIGNING_SECRET`, `BASE_URL`, and friends (see `runtime.exs`).
- `MyApp.SentryEventFilter` filters events before they reach Sentry.
- Formatter plugins: Spark, LiveView HTML, TailwindFormatter, Styler, and `MyApp.Prettier`. `.doctor.exs` requires 100% moduledoc coverage.
- **`mix format` also formats JS/TS.** `.formatter.exs` registers `tag_formatters: %{script: MyApp.Prettier}`, so the body of every `<script>` tag in a HEEx template — colocated hooks included — is piped through prettier (run via `bun run`) from `assets/node_modules`, with `assets/.prettierrc` (printWidth 100) applied. The parser follows the tag's `extension` attribute, which is why TypeScript hooks must carry `extension="ts"`. If `assets/node_modules` is missing, script bodies are left untouched and a warning is logged; run `mix assets.setup`.
- That module is **also listed under `:plugins`**, where it declares no sigils and no extensions and formats nothing. Only plugins make `mix format` load — and, when the beam is missing, compile — a project module; a `:tag_formatters` entry it cannot find is merely logged as `module ... is not loaded and could not be found` and silently skipped. Keep it in both lists.
- **After changing `assets/.prettierrc` or the tag formatter, run `mix format --force`**: a bare `mix format` only revisits files whose mtime is newer than the last run, and neither of those counts as a source that invalidates that cache (`.formatter.exs` and `mix.exs` do). `mix format --check-formatted` never uses the cache, so a skipped file surfaces as a CI failure.

## Testing

- `MyApp.DataCase` — SQL sandbox (`start_owner!`, async-aware), `use Oban.Testing` (Oban runs `:inline` in test), `errors_on/1`. `MyAppWeb.ConnCase` builds on it with `Phoenix.ConnTest` and verified routes.
- **Fixtures**: `MyApp.AccountsFixtures.user_fixture/1` creates users through the real `:register_with_sso` action with `authorize?: false`, seeding a realistic OIDC `user_info` map; pass `roles: ["admin"]` for admins. Test env compiles with `:oidc_enabled, true` so the `:sso` strategy exists.
- **Authenticated conn tests** — no `log_in_user` helper; use AshAuthentication's plug helpers directly:

```elixir
import AshAuthentication.Plug.Helpers
conn |> init_test_session(%{}) |> store_in_session(user) |> get(~p"/oban")
```

- Component tests render with `render_component(&Combobox.combobox/1, assigns)` and assert on HTML; LiveView tests use `live/2` + `has_element?/3`.
- `mix test` runs `ash.setup --quiet` first; JUnit reports land in `test/reports/` (CI).

## Template mechanics

`mix template.setup <Name>` (an Igniter task in `lib/mix/tasks/template.setup.ex`) renames the whole template — `MyApp`/`MyAppWeb`/`my_app`/`my-app`/`MY_APP` across `lib`, `test`, `config`, `assets`, `priv`, `rel`, `helm`, CI, Dockerfile and README — and moves the `lib/my_app*`, `test/my_app*`, and helm chart directories.

This section is about bootstrapping a _new_ project from the template, not about working in this repository day to day. If you're an agent asked to start a real project from this template: run the task once, then fill in [PROJECT.md](PROJECT.md) with the new product's context.
